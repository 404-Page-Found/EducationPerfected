# Publishing v2026.11.15 (owner steps)

CI never tags, releases or publishes. After the internal test build passes on your machine:

1. Save an EMPTY draft release on GitHub: tag `v2026.11.15`, name v2026.11.15, target the release commit. Paste the full commit SHA as the target so a moving main cannot retarget the build; a branch target is resolved once, when the Publish run starts. Paste the content of `release/release-notes-2026.11.15.md` as the body.
2. Actions -> Publish -> Run workflow with tag `v2026.11.15`. The workflow resolves the commit from the release itself, then either attaches the verified staged bundle for that exact commit or, when none exists, builds the five native candidates from that commit with every validation lane, assembles the bundle byte-identical to the validated candidates, verifies it (22 files: 21 payloads + SHA256SUMS), and attaches it. The draft STAYS a draft, and npm publication is skipped while it is one. main may move at any point; the run never follows it.
3. Review the draft's attached files (5 raw executables, `educationperfected-windows-x64-setup.exe`, 2 `.pkg`, 2 `.deb`, 2 `.rpm`, `educationperfected-2026.11.15.tgz`, `install.sh`, `install.ps1`, the 5 notices zips, `release-notes.md`, `SHA256SUMS`; download and `sha256sum -c SHA256SUMS` to verify), then publish manually.
4. Alternatively, publish the release empty. Publish then runs automatically on the published release and attaches the same verified files, but only while it has zero assets; a published release with assets is never modified. The button also accepts a zero-asset published release, so a failed publish-first run can be retried without deleting the release. Draft-first stays the default: the files can be reviewed before anyone sees them.
5. npm: nothing to run by hand. When the release is published (step 3 or 4), the Publish workflow's `release:published` run leaves the attached files untouched and its `npm-publish` job publishes the package to the npm registry: it downloads `educationperfected-2026.11.15.tgz` back from the release, re-verifies it against the release's `SHA256SUMS` (so the registry gets the exact bytes that were validated and attached), skips the publish if that version is already on the registry, and only ever runs once the release is live, because the package's postinstall downloads the platform binary from the release. One-time setup before the first publish: add an `NPM_TOKEN` repository secret (npmjs.com -> Access Tokens -> Granular Access Token with Read and write on packages) - the first publish needs it, because npmjs.com only offers trusted publishing for a package that already exists. To replace the token afterwards: configure trusted publishing (npmjs.com package settings -> Trusted Publisher: 404-Page-Found / EducationPerfected / publish.yml, allowed to `npm publish`), set the `NPM_TRUSTED_PUBLISHING` repository variable to `true`, and delete the secret. With neither the secret nor the variable, the job fails before publishing with these setup steps. If the job fails after the files were attached, fix the credentials and use "Re-run failed jobs" - only `npm-publish` runs again. Verify afterwards: `npm view educationperfected`.
6. The updater sees the release as soon as it is non-draft/non-prerelease with the five `educationperfected-<target>` assets plus `SHA256SUMS`; the extra assets are ignored by it.
